# ③ 입력 → 처리 → 출력 계약

## 3-1

| 항목 | 내 작성 |
| --- | --- |
| 입력 | 개체쌍 하나(질병 + 약물/증상)와, 그 쌍이 함께 등장한 임상 노트 전문 + `note_id`. 노트는 구분선으로 감싸 데이터임을 표시한다 |
| 처리 | 후보 재계산 → 노트 묶기 → LLM 판정 → JSON 파싱 → 스키마 검증 → 인용문을 노트 원문과 대조 → 주입 탐지 → 라우팅 |
| 출력 | `relation`(treats / has_symptom / no_relation), `evidence[]`(quote + note_id), `confidence`, `abstained`, `abstention_reason`, 그리고 라우팅 결정 하나 |

계약은 `schemas/verdict.py`가 강제한다. 보류인데 근거를 넣거나, 관계를 인정하면서 근거를
비우면 파싱 단계에서 죽는다 — "잘 모르겠지만 아마 X일 것"이 통과하지 못하게 하려는 것이다.

## 3-2

| 질문 | 내 작성 |
| --- | --- |
| 어떤 모델·기술로 처리하는가 | `nvidia_nim/openai/gpt-oss-20b`. 프롬프트에 출력 계약과 판정 절차를 적고 JSON만 받는다 |
| 왜 그것을 골랐는가 | 후보 4종을 같은 케이스로 재본 결과 유일하게 **code fence 없이 JSON만** 반환했고 지연이 4.8s로 가장 짧았다. 근거 수치는 `configs/relation-nim.yaml` 주석에 남겼다 |
| 대안은 무엇이었고 왜 안 골랐는가 | `llama-3.3-70b`는 82s로 103건에 141분이 들고, `llama-3.1-8b`는 JSON 뒤에 설명을 덧붙여 파싱이 깨졌다. 규칙 기반 동시출현 컷은 **버린 이유가 따로 있다** — 잡음컷을 2로만 올려도 진짜 관계 5건이 모델에 닿기 전에 사라진다(`docs/operating-point.md` 2절) |

## 3-3 출력의 뜻과 뜻하지 않는 것

| 화면 표현 | 뜻 | 뜻하지 않는 것 |
| --- | --- | --- |
| `has_symptom` 판정 | **노트가 그 관계를 진술했다**는 표시 | 의학적으로 사실이다, 인과관계다 |
| `confidence 0.95` | 모델이 스스로 매긴 값 | 정답 확률 95%. validation에서 0.90·0.95·1.00 구간의 오답률 차이가 거의 없었다(`docs/operating-point.md` 3절) |
| `✓ 근거 검증됨` | 인용문이 노트 원문과 0.8 이상 일치한다 | 그 인용이 판정의 실제 근거다 (그건 절제가 따로 잰다) |
| `✓ 근거 제거 시 판정 뒤집힘` | 그 문장을 빼니 판정이 달라졌다 | 인과적 설명이다 (`day6 p17`) |
| `PPV 1.0` | 화면에 뜬 관계 9건이 모두 맞았다 | 헛경보가 없다. **헛경보를 관측할 기회가 9번이었다**는 뜻이다 |
| `no_relation` | 노트가 관계를 진술하지 않았다 | 그런 관계가 존재하지 않는다 |

# ④ 운영점

## 4-1

| 질문 | 내 작성 |
| --- | --- |
| 어떤 값을 기준으로 자르는가 | 두 개다. `min_cooccur`(개체쌍이 몇 개 노트에 함께 나왔나)와 모델의 `confidence` |
| 시작 기준값 | `min_cooccur = 1`(잡음컷 없음), `confidence ≥ 0.95`. **validation 41건에서 골랐다** |
| 이 값 위·아래를 무엇으로 나누는가 | 위 + 관계 인정 → 화면 자동 표시 / 위 + 관계 없음 → 조용히 버림 / 아래 또는 보류 → 사람 확인 큐 |

선택 규칙은 정확도 최대화가 아니다. **PPV ≥ 0.95를 제약으로 걸고** 그 아래에서 자동표시된
정답 관계 수를 최대화했다(`evaluation/operating_point.py:select_operating_point`).

## 4-2

| 질문 | 내 작성 |
| --- | --- |
| 기준값을 낮추면 무엇이 늘어나는가 | `confidence`를 0.90으로 낮추면 큐가 9 → 4건으로 줄지만 **무성 놓침이 5 → 8건으로 늘어난다.** 사람이 볼 기회 자체가 사라지는 건이 늘어난다 |
| 기준값을 높이면 무엇을 놓치는가 | 1.00으로 올리면 자동표시가 7 → 3건으로 반토막 나고 큐가 41건 중 32건이 된다. 그 지점에서는 사실상 아무것도 자동화하지 않는다. `min_cooccur`를 2로 올리면 후보 14건이 모델에 닿기도 전에 사라지고 그중 5건이 진짜 관계다 |
| 놓침과 헛경보 중 더 피해야 할 것은 | **헛경보** — 잘못된 약물-질병 연결이 그래프에 등록되면 지워지지 않고 계속 재사용된다. 놓친 관계는 다음 노트에서 다시 후보로 올라올 수 있지만, 등록된 오류는 스스로 사라지지 않는다 |

**정직하게 덧붙일 것** — 이 설정에서 confidence 임계값은 실제로는 손잡이가 아니었다.
모델이 validation에서 헛경보를 한 건도 내지 않아 PPV 제약이 격자 어느 칸에서도 구속력이
없었다. 임계값이 실제로 맞바꾸는 것은 정밀도가 아니라 **무성 놓침과 큐 길이**다.

### ④ 완료 확인

- [x] 무엇을 기준으로 자르는지와 시작 기준값을 적었다.
- [x] 값을 낮출 때와 높일 때 각각 무엇이 달라지는지 적었다.
- [x] 놓침과 헛경보 중 더 피해야 할 것을 근거와 함께 골랐다.

# ⑤ 무너지는 지점과 대응

## 5-1

| 번호 | 무너지는 상황 | 어디서 탐지하는가 | 어떻게 대응하는가 |
| --- | --- | --- | --- |
| 붕괴 1 | **노트 본문에 모델에게 주는 지시문이 섞여 들어온다** (OWASP LLM01) | 노트 텍스트를 규칙으로 검사한다 — 지시 무시 요구, 시스템 프롬프트 유출 요구, 근거 날조 요구, 역할 전환 | 모델이 지시를 물리쳤더라도 `DRAFT_REVIEW_INJECTION` 큐로 보낸다. 저항과 탐지는 다른 것이라 따로 센다 |
| 붕괴 2 | **모델이 조정 때 보지 못한 문형을 만난다** | split별 문형 구성을 세어 development가 담지 않은 문형을 찾는다 | 프롬프트를 고치지 않고 예측을 먼저 등록한 뒤 최종 실행으로 대조했다. 재발 방지는 문형 기준 층화다 |
| 붕괴 3 | **인용문을 지어낸다** | 인용문을 노트 원문과 대조해 0.8 미만이면 게이트에서 막는다 | `REJECT_GROUNDING`. 원본 저장소는 검증 불가 시 게이트를 건너뛰지만 여기서는 우회 경로를 두지 않았다 |

붕괴 2는 가정이 아니라 **실제로 일어났다.** validation 실패 8건이 development가 한 번도
담지 않은 두 문형(PRESENTED 단독, HEDGE 단독)에 예외 없이 몰렸다. development가 담은 네
문형은 100% 통과, 담지 않은 두 문형은 0% 통과다.

## 5-2

| 질문 | 내 작성 |
| --- | --- |
| 붕괴가 감지되면 화면은 무엇을 하는가 | 자동 표시를 하지 않고 사유가 붙은 큐로 보낸다. `no_relation`을 "관계 없음 확정"으로 표시하지 않는다 |
| 사람은 무엇을 확인하는가 | 큐레이터가 노트 원문 전체와 인용문 대조 결과를 보고 등록/버림을 정한다. 주입 큐는 노트 자체를 코퍼스에서 뺄지까지 판단한다 |

**validator 체인이 못 잡는 것도 적는다** — validation 실패 8건이 전부 `DRAFT_REVIEW`로 갔다.
스키마도 맞고 인용도 원문과 대조된다. **판정 내용이 틀린 것은 체인이 잡을 수 없다.**
이것이 사람 검토를 없앨 수 없는 이유이고 PPV를 제약으로 건 이유다.

# ⑥ 장비·소스 변화 대응

## 6-1

| 질문 | 내 작성 |
| --- | --- |
| 어떤 변화를 가정하는가 | 다른 기관의 임상 노트가 들어온다. 지금 코퍼스는 **6개 템플릿 문형**으로 생성된 합성 데이터이고, 실제 노트는 문형이 정해져 있지 않다 |

| 사람은 무엇을 확인하는가 | 새 코퍼스에서 문형 분포를 먼저 세고, 지금 라벨링 규칙(`data/labeling_rules.py`)이 그 문형을 덮는지 확인한다. 덮지 못하면 라벨링 규칙부터 다시 만든다 |

**추가로 정한 것** — 절제(XAI) 결과도 도메인을 탄다. 지금 문장 경계는 규칙 분리이고 노트가
템플릿이라 잘 맞는다. 일반 임상 노트에서는 문장 분리부터 다시 봐야 한다.

**초과한 것을 그대로 적는다** — 단일 HTML 한 개이지만 탭이 5개다(요약 · 케이스·근거 ·
두 임계값 · 검토 큐 · XAI 절제). 워크시트가 말하는 "화면 1~2개"의 취지보다 넓다. 넓힌
이유는 두 임계값을 한 화면에서 보이라는 `day3 p40` 요구와 근거 패널 확장 요구가 같은
탭에 다 들어가지 않아서다. 좁히라면 **케이스·근거 탭 하나만 남기는 것**이 핵심이다.

# 설계 확정 게이트

| 게이트 | 질문 | 내 답 |
| --- | --- | --- |
| 1 | 사용자는 이 결과를 보고 무엇을 결정하는가 | 후보 관계를 그래프에 **등록**할지, **버릴지**, **노트 원문을 직접 확인**할지를 고른다. 화면의 라우팅 값이 그 세 갈래로 미리 나눠져 있다 |
| 2 | 이 기술을 빼면 어떤 화면 기능이 사라지는가 | 근거 절제를 빼면 "이 인용이 실제 판단 근거였나"를 말해주는 줄이 사라져 인용문은 있으나 그것이 장식인지 알 수 없게 된다. 주입 탐지를 빼면 전용 큐가 사라져 지시문이 섞인 노트가 일반 건과 같은 줄에 선다 |
| 3 | 데이터가 바뀌거나 결과가 틀렸을 때 이 서비스는 계속 자동으로 작동하는가 | **아니다.** 스키마·근거 게이트에서 막히면 결과를 표시하지 않고, 주입이 탐지되면 저항 여부와 무관하게 전용 큐로 보내며, 통과한 건조차 `DRAFT_REVIEW`다. 라우팅 타입에 `APPROVED`가 없어서 자동 확정에 도달할 경로 자체가 없다. 소스가 바뀌면 정확도 칸을 비우고 "성능을 잴 수 없다"로 표시한다 |

## 게이트 통과 기준 대조

- **게이트 1** — 고를 수 있는 구체적 행동(등록/버림/원문확인)이 나왔다. "도움이 된다"가 아니다. ✅
- **게이트 2** — 기술 이름을 나열하지 않고 빠질 때 사라지는 화면 기능을 지목했다. ✅
- **게이트 3** — 경고할지·사람에게 넘길지·멈출지가 라우팅 값으로 정해져 있고 타입으로 강제된다. ✅

## 이 설계서에서 스스로 지키지 못한 것

워크시트를 채우면서 드러난 것을 숨기지 않고 적는다.

1. **development split을 문형 기준으로 층화하지 않았다.** support 기준으로만 나눈 탓에
   6개 문형 중 2개가 조정 단계에 한 번도 들어가지 않았고, 그 두 문형에서 정확도가 0이
   나왔다. ⑤ 붕괴 2가 가정이 아니라 실제 사건인 이유다.
2. **절제 결과를 한 번 부풀렸다.** 인용문이 노트 전부여서 필요성을 물을 수 없는 12건을
   "판정이 뒤집혔다"로 세어 FAITHFUL이 22건으로 나왔다. 자동으로 참이 되는 값을 성공으로
   센 것이라 `NECESSITY_VACUOUS`로 갈라내니 10건이 됐다.
3. **탭을 5개로 늘렸다.** 워크시트가 요구한 화면 범위보다 넓다(7-1).

세 가지 모두 결과에 그대로 남겨 뒀고 고친 흔적도 문서로 남겼다. 설계서가 잘된 것만 적는
문서가 되면 ⑤와 ⑥이 하는 일이 없어진다.
